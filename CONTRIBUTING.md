# Contributing

Thanks for looking. This is an open re-implementation of a published system, so
the bar is the same as the bar for the paper: things should be checkable.

## Getting set up

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
co-scientist init
co-scientist doctor
```

`doctor` has to report a ready backend before anything interesting works. You
need either an API key or a subscription CLI signed in. See the
[LLM backend](README.md#llm-backend) section.

Python 3.11 to 3.13. The ceiling is set by FAISS wheel availability.

## Before you open a pull request

```bash
ruff check co_scientist scripts
pytest co_scientist/tests/unit -q
python scripts/validate_plugin.py     # if you touched plugin/
```

CI runs the same three on 3.11, 3.12 and 3.13.

## What a good change looks like

**Tests come with the change, not after.** Every unit test in this repo runs
offline: no API key, no network, no subscription quota. Use the fakes in
`co_scientist/tests/fakes/` rather than reaching for a real provider. A test
that needs a key belongs in `tests/smoke/`, which is not part of CI.

**Behaviour changes get a test that fails without the change.** Especially for
anything touching Elo, the task queue, dedup, or the storage schema. Those are
the parts where a silent regression is expensive and invisible.

**Storage changes go through a migration.** Add a numbered file under
`co_scientist/storage/migrations/`. The runner is idempotent; do not edit
`schema.sql` in place for anything already released.

**Prompts are derived from the paper.** `config/prompts/` follows the paper's
supplementary prompts modulo Jinja interpolation. If you change one, say in the
pull request what the paper says and why the change is an improvement rather
than a drift.

## Working on the Agent Plugin

`plugin/` is an [Agent Plugins 1.0](https://agent-plugins.org/specification)
package. Two checks guard it:

- `python scripts/validate_plugin.py` checks spec conformance: manifest fields,
  transport types, skill frontmatter, name and directory agreement, body
  length, and that every relative link resolves and stays one level deep.
- `co_scientist/tests/unit/test_plugin.py` checks the part a validator cannot:
  that no skill instructs an agent to call an MCP tool or CLI command that does
  not exist.

If you add an MCP tool, document it in a skill. A tool no skill explains is a
tool an agent will use badly.

If you add a skill, keep the SKILL.md body under 500 lines and push detail into
`reference/` files linked directly from SKILL.md. Descriptions are routing
rules, written in the third person, naming the triggers and the output. See
[Anthropic's skill authoring guide](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)
for the reasoning.

## Reporting a bug

Include the output of `co-scientist doctor` and, for anything that happened
during a run, the session id and the relevant lines from
`data/logs/session-<id>.jsonl`. Strip your keys first.

## Bench results

`docs/BENCH_RESULTS.md` is generated by `python scripts/build_bench_report.py`
from the bench tables. Do not hand-edit it. If you run a bench worth sharing,
regenerate the file and include the run in the pull request so the numbers stay
traceable to the data that produced them.

## Scope

This is a re-implementation, not a fork of the paper's system, and not
affiliated with its authors. Changes that make the implementation clearer,
faster, cheaper or better tested are welcome. Changes that quietly diverge from
the paper's architecture should say so explicitly in the pull request, so the
divergence is a decision rather than a drift.
